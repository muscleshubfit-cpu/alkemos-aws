### 3.2 من كان أدمنًا فعلًا عبر التاريخ (برهان tool_leads)

بذر 0060 (نُفّذ 2026-09-01T01:12:45) اشتق `tool_leads.type` من **الدور الحي لحظة التنفيذ**: `case p.role when 'admin' then 'admin'…`. الصفوف الحية:
- `speerr@gmail.com` → **type='admin'`** ⇒ كان أدمنًا يوم 2026-09-01 ✓ (نتيجة الترقية الجماعية 0029B يوم 2026-08-29)

### 3.3 أضيق نافذة زمنية للحادثة (برهان admin_notifications)

مسار `coach/register` يرسل إشعار «مدرب جديد سجّل بنفسه» إلى أول `role='admin'` بترتيب `created_at`:
- إشعار **2026-10-05T20:29:18** (تسجيل Osama) استهدف uid **speerr** (`7c5d2428…`) — وحينها كان أدمن QA (أُنشئ 09-07، أي أحدث من speerr) لا يزال موجودًا؛ فلو لم يكن speerr أدمنًا لكان الهدف حساب QA — **⇒ speerr كان أدمنًا في 2026-10-05 20:29 UTC**
- الحادثة إذن بين **2026-10-05 20:29** و **2026-11-05 12:45 UTC**. اللحظة/الفاعل الدقيقان: **غير قابلَين للاسترجاع** — `profiles` بلا `updated_at` ولا أي سجل لتغييرات الدور (فجوة المراقبة — أُغلقت بـ0105).

## 4) السبب الجذري (مثبت بالمسبارات الحية)

### 4.1 خريطة الانحراف الحية (مسبار سلوكي بحساب اختبار مؤقت — أُنشئ واستُخدم وحُذف بالكامل)

| العنصر الأمني | المتوقع (المعتمد) | المقيس حيًا **قبل** الإصلاح | الحكم |
|---|---|---|---|
| `handle_new_user()` (تريغر التسجيل) | 0036: الدور دائمًا client، metadata العميل تُهمل | تسجيل بميتاداتا `role:'admin'` → وُلد الصف **client** | ✓ سليم |
| `is_admin()/is_coach()/is_staff()` | 0029B: الأدمن يحقق الثلاثة | أدمن تجريبي: الثلاثة **true** | ✓ سليمة |
| `auto_promote_coach_if_allowed()` | 0029B: ترقية client→coach فقط، لا يُنزَل أدمن | أدمن تجريبي + بريد مدرج → HTTP 200 والدور **بقي admin** | ✓ سليم |
| **`profiles_update_self`** | 0017: `WITH CHECK` يمنع تغيير الدور ذاتيًا | **مستخدم يغيّر دوره بنفسه عبر PostgREST → HTTP 200/204 — بلا أي قيد** | ✗ **انحراف حرج** |

**الانحراف المُثبت هو الثغرة نفسها**: أي مستخدم مصادق (بأي دور) يستطيع منذ لحظة غير معلومة كتابة دوره بنفسه — **بما في ذلك الترقية الذاتية إلى admin** (تصعيد صلاحيات)، وليس فقط ما حدث لصاحب الحساب. القيمة `204` المقيسة تعني أن القيد المفروض منذ 0017 (وأُعيد تطبيقه بعد حادثة Phase-61 بـ0055) لم يعد موجودًا على الإنتاج — **نفس صنف الانحراف الصامت الذي حدث في Phase-61** (إعادة تشغيل تعريفات قديمة تُلغي التحصينات بلا أي إشارة فشل)، والبوابات القائمة لم تكن تراه: بوابة الحالة تتحقق من الميجريشن **الأحدث** فقط، لا من تعريفات الكائنات الحية.

### 4.2 كيف تترجم الثغرة إلى الحادثة الملاحظة

- السياسة المنحرفة تقصر الكتابة على **صف المستخدم نفسه** (`using auth.uid()=id`) + السياق الخدمي يتجاوز RLS كليًا. كل كود التطبيق بُرّئ (المسارات الإدارية تحرس الأدمن صراحةً؛ وآثارها الجانبية غائبة عن حساب speerr — §2.2)، فالكتابة الفعلية جاءت من: تعديل SQL يدوي من لوحة Supabase، أو استدعاء مصنوع بجلسة صاحب الصف نفسه عبر الثغرة. الحالة النهائية `coach` متسقة مع المسار المصمم: `admin → (كتابة خارجية عبر الثغرة) → client → أول دخول يشغّل الترقية التلقائية المصرّح بها client→coach` (أُعيد إنتاج التسلسل كاملًا حيًا بالمسبار F قبل الإصلاح: النتيجة النهائية coach حرفيًا).
- **لماذا «متكررة»؟** لأن الإصلاحات السابقة (0017 ثم 0055) كانت تعيد صياغة **السياسة** وحدها: خط دفاع واحد، بلا حارس مستوى القاعدة، بلا سجل يكشف أي تجاوز، بلا بوابة تراقب حيوية التعريف نفسه — فعاد الانحراف مرة ثانية بصمت ولم يكن هناك ما يكشفه أو يوقفه.

### 4.3 المسارات المُبرّأة (بالأدلة، لا بالافتراض)

| المسار | البرهان |
|---|---|
| `POST/PATCH /api/admin/staff` | الترقية تقلب `tool_leads.type` إلى coach لبريد المالك (مقيس: صف speerr لا يزال `type='admin'`) والتنزيل يحذف صف `coach_emails` (مقيس: صفه محفوظ منذ 2026-08-26) — كلا المسارين لم يُطلق على الحساب قط |
| `/api/coach/register` | يرفض البريد المسجل 409 قبل أي كتابة |
| `fetchProfile` (المتصفح) | بوابة `role==='client'` موجودة بكل النسخ التاريخية (تتبع git) — لا تكتب دورًا أبدًا وهي تقرأ admin؛ وفرع إعادة الإنشاء يولّد client/coach فقط (لا يمكنه منح أو إسقاط admin — عولج مع ذلك في 0105) |
| تريغر التسجيل / الاستدعاءات الخادمية الأخرى | تحرسها الفحوص الحية §4.1 (كلها بالتعريفات المعتمدة) |

## 5) الإصلاح المنفذ — الميجريشن 0105 ADMIN-ROLE-INTEGRITY

> القناة: خط الترحيل المملوك (migrate job بـdeploy-aws → `SUPABASE_DB_URL`، قبل نشر الكود) — لا SQL يدوي. قانون الميجريشن كامل بنفس الكوميت: صف INDEX.md + مرآة types.ts + فحوص migration_probes.

| الجزء | ماذا يفعل | أي فجوة جذرية يغلق |
|---|---|---|
| **1. `role_audit_log`** | كل تغيير دور (ولادة بدور ستاف/تغيير/حذف صف أدمن) يُسجَّل: الفاعل (uid+email أو null للسياق الخدمي) + القديم/الجديد + اسم القناة المصرّحة + الطابع الزمني. قراءة للأدمن فقط (RLS)، كتابة من التريغر حصرًا، **بلا FK عمدًا** (السجل يبقى بعد حذف البروفايل) | غياب المراقبة — أي حادثة مستقبلية تُنسب لفاعل ولحظة فورًا |

| **8. استعادة `speerr@gmail.com` → admin** | بعد تفعيل التدقيق فيصبح الاستعادة **أول سطر بالسجل** (سياق `0105-restore`) — محروسة بالبريد حرفيًا وidempotent | أمر المالك الصريح، بالطريقة الموثقة لا اليدوية |

## 6) حراسة الإصلاح ذاته (منع التكرار بنيويًا)

فحوص 0105 المضافة لبوابة الحالة (تعمل مع كل push + يوميًا 06:10 UTC عبر جلسة أدمن اختبارية مؤقتة تُنشأ وتُحذف بنفس التشغيلة):

1. `swagger_table role_audit_log` — السجل حي.
2. `swagger_rpc admin_set_user_role` — القناة حية.
3. `at_least_one_admin` — **الإنتاج لن يحمل صفر أدمن مرة أخرى دون أن تحمرّ البوابة في نفس اليوم**.
4. `self_role_patch_rejected` — **حارس الانحراف**: جلسة الأدمن المؤقتة تحاول تغيير دورها بنفسها عبر PostgREST — المتوقع رفض 4xx؛ لو سمحت القاعدة يومًا (عاد انحراف السياسة أو أُسقط التريغر) تلوّن البوابة فورًا بصيغة «ROLE-WRITE DRIFT». هذا تحويل الحادثة نفسها إلى اختبار يومي.

| T6 | metadata التسجيل مهملة | مستخدم جديد بميتاداتا `role:'admin'` وُلد **client** ✓ |
| T7 | **حارس آخر أدمن (قناة الـRPC)** | محاولة تنزيل المالك عبر `admin_set_user_role` بسياق خدمي → **HTTP 400 (23514) «refusing to demote the LAST admin»** والدور بقي admin ✓ |

## 8) المخاطر المتبقية (بصدق كامل)

1. **تحديد الفاعل الأصلي للحادثة مستحيل رجعيًا** — الأدلة التاريخية لا تتضمن سجل كتابة الدور (كان غير موجود). أُغلقت الفجوة من الآن فصاعدًا: كل تغيير دور مستقبلي موثّق بفاعل وقناة ولحظة.
2. **السياق الخدمي (service-role / SQL Editor) يبقى قادرًا على تغيير الأدوار بالتصميم** (قناتا التطبيق المشروعتان) — الحارس يقصر ذلك على: أدمن (للـRPC) أو مفتاح الخدمة (لا يملكه إلا المالك وسير العمل المصرّح) — ولا يمكن لأي منها أن يُنزّل **آخر** أدمن.
3. **انحراف التعريفات صنف Phase-61 ممكن نظريًا ما دام هناك تكامل/إعادة تشغيل خارجية** — لكن حارس الانحراف اليومي (§6.4) يجعل عمره الصامت ≤24 ساعة بدل أسابيع، وحارس «يوجد أدمن» يمنع أسوأ نتيجة نهائية بغض النظر عن السبب.
4. **لا مرآة زمنية للحظة الحادثة** داخل النافذة (10-05→11-05): إن وُجدت سجلات Cloudflare/خادم محفوظة لدى المالك يمكن تضييقها لاحقًا بأمر مستقل — ليست شرطًا للإصلاح (الإصلاح لا يعتمد على الفاعل).
