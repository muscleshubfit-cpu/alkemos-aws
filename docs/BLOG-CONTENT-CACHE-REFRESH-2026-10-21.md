# BLOG-CONTENT-CACHE-REFRESH 2026-10-21 — انعكاس التعديلات اليدوية والاعتمادات على المقالات المنشورة (المرحلة 359)

> **أمر المالك (2026-10-21):** «افحص سبب عدم انعكاس تعديلاتي اليدوية على المقالات المنشورة في Alkemos، واستمرار ظهور محتوى قديم وحالة «مولّد بالذكاء الاصطناعي وفي انتظار المراجعة» رغم أنني راجعت المقالات واعتمدتها. تتبّع دورة البيانات كاملة من قاعدة البيانات وحالة المراجعة إلى مصدر الصفحة والاستجابة الحية، وحدد السبب الجذري لكل مشكلة… أصلح السبب الجذري بأقل تغيير آمن، دون تعديل إعدادات الكاش العامة أو تغيير سياسة المراجعة المتفق عليها… وثّق السبب والإصلاح ونتائج التحقق، ونفّذ النشر الفعلي إذا لزم.»

## §1 الخلاصة التنفيذية

**التعديلات والاعتمادات كانت محفوظة وسليمة طوال الوقت — القاعدة والـ origin كانا يحملان الحقيقة، وكاش الحافة (Cloudflare) هو الذي كان يقدّم النسخة ما قبل التعديل للزوار.** القياس الحي المباشر أثبت أن كل طبقة كانت تقول شيئًا مختلفًا عن التي تليها في اللحظة نفسها (§3)، والسبب الجذري التصميمي: **ثلاث طبقات TTL متراكبة بلا أي خطاف إبطال واحد في الكود كله** (grep: صفر `revalidatePath`/`revalidateTag` في المستودع) — فأي كتابة للمالك (اعتماد/تحرير) لا تصل للقارئ إلا بانتهاء نافذة القِدم التراكمية، وقد تمتد ساعات مع `stale-while-revalidate` الطبقيّة (طبقة تُثبِّت قِدم الطبقة التي قبلها). المعالجة الفورية نُفّذت حيًّا (تنقية مستهدفة لرابطَي المقالين → ظهور التعديلات والاعتماد فورًا، مقيس أدناه)، والإصلاح الجذري الدائم (بأقل تغيير آمن، TTLs وإعدادات الكاش وسياسة المراجعة كلها بلا أي مساس): **كل مسار كتابة للمالك صار يُبطل الطبقات الثلاث لحظة نجاحه** — tags لذاكرة البيانات + revalidatePath لصفحات ISR + purge مستهدف لحافة Cloudflare.

## §2 دورة البيانات الكاملة (كما قيست حيًّا)

```
قارئ المتصفح
  └─ Cloudflare edge (HTML: s-maxage=3600, stale-while-revalidate=86400)   ← كان هنا القِدم
       └─ Caddy → Next.js origin
            ├─ ISR page cache (revalidate=3600, generateStaticParams)       ← كان متجددًا
            ├─ Data cache: unstable_cache ×3 (revalidate=3600)              ← كان متجددًا
            │    ├─ fetchBlogForOG      ["blog-og"]
            │    ├─ fetchBlogPostFull   ["blog-full"]
            │    └─ slugPools           ["blog-slug-pools"]
            └─ Supabase blog_posts (السلطة الوحيدة)                          ← كانت تحمل الحقيقة دائمًا
```

مسارات الكتابة على `blog_posts` قبل هذا الإطار (كلها بلا أي إبطال):
`POST /api/admin/blog/review` (زر «اعتماد») · محرر المدونة `adminUpdatePost`/`adminCreatePost` (من المتصفح إلى Supabase مباشرة — لا يمر بخادم التطبيق أصلًا) · تعديلات Supabase Dashboard اليدوية · P5 pipeline (من GitHub Actions).

## §4 السبب الجذري

**السبب القريب (ما رآه المالك):** حافة Cloudflare تقدّم لنسخة HTML ما قبل التعديل على العناوين الأساسية حتى انتهاء `s-maxage=3600`، و`stale-while-revalidate=86400` تسمح بخدمة القديم أثناء التحديث الخلفي — وبما أن الأصل نفسه يخدم أحيانًا صفحة ISR STALE-أثناء-التجديد (وهي 200 تُعاد الكاشة ساعةً أخرى عند الحافة)، **يمكن للطبقات أن تُثبِّت قِدم بعضها فتتجاوز التأخير عمليًا ساعات** مع حركة زيارة متقطعة.

**السبب التصميمي (الجذر):** مسارات كتابة المالك تعدّل القاعدة ثم تعود فورًا — **لا يوجد في الكود كله أي استدعاء `revalidatePath`/`revalidateTag`** (قبل هذا الإطار: grep = 0)، ومدخلات `unstable_cache` الثلاث بلا `tags` فلا يمكن إبطالها حتى لو استُدعي المسار. النظام كان يعتمد كليًا على انتهاء TTL التراكمي (ساعة بيانات + ساعة ISR + ساعة حافة، بلا أي قناة دفع) — وهذا ما عاشه المالك: «راجعت واعتمدت ولا شيء يتغير».

**ما لم يكن سببًا (مُستبعد بالقياس):** التعديلات لم تُحفظ؟ (E4 تنفي) · نسخ متكررة؟ (E4: صفر) · آلية توليد تعيد بيانات قديمة؟ (E5 ينفي) · سياسة المراجعة نفسها؟ (تعمل حرفيًا كما صُممت — 0097 — والشارة كانت صادقة على الحالة القديمة للصف فقط).
