## 5) خطوة المالك الوحيدة (مرة واحدة — دقيقتان)

**المسار أ (يجعل المستودع مكتفًا ذاتيًا للأبد):**
1. لوحة Supabase → المشروع → **Settings → Database → Connection string → URI** (انسخه).
2. GitHub → الريبو → **Settings → Secrets and variables → Actions → New repository secret** → الاسم `SUPABASE_DB_URL` والقيمة الرابط.
3. شغّل workflow ‏`DB migrate` (Dispatch) — يطبق المعلق بالترتيب ويتحقق؛ ومن أي دفعة تالية يطبق تلقائيًا ضمن مسار النشر نفسه.

**المسار ب (إحياء التكامل القديم):** لوحة Supabase → Integrations → GitHub → إعادة ربط المستودع؛ الدفعة التالية تلتقط المتراكم — وبوابة الحالة تظل تراقب للأبد (لو مات ثانية نرى أحمر فورًا).

**المسار اليدوي (ملاذ أخير بنمط §6):** `RUN_ON_SUPABASE_0102_sub_pick_active_first.sql` موجود ومطابق حرفيًا للملف المؤرخ (فُحص diff) + `NOTIFY pgrst, 'reload schema';` — سلّمته جولة 372 وهو متاح، لكن أمر المالك 2026-10-27 صريح: **ليس حلًا نهائيًا** — القناتان أ/ب أعلاه هما الحل الدائم، واليدوي يظل أداة طوارئ فقط.

**أسرار الفحص السلوكي:** ‏`QA_PROBE_EMAIL` + `QA_PROBE_PASSWORD` (حساب أدمن الاختبار القياسي `qa.admin@alkemos-test.com` — قناة حسابات الاختبار) **معيّنة بالفعل كأسرار Actions** في هذا الفريم — البوابة جاهزة.

## 6) قوانين الأمان الدائمة

- الدفتر (`supabase_migrations.schema_migrations`) هو مصدر «ما هو مطبق» الوحيد — المسجل لا يُعاد تشغيله أبدًا.
- عائلة التطبيق: `YYYYMMDDHHMMSS_NNNN_<slug>.sql` + الرقمية القديمة 0001..0005 فقط — `RUN_ON_*`/`VERIFY_*` يدوية كما هي (INDEX §1).
- إصلاح انحراف الدفتر: `--mark-applied <versions>` (نمط 0054 المحبَّب) — أبدًا ليس بإعادة تشغيل تاريخ أقدم من الأرضية.
- نجاح نشر الكود ليس دليلًا على تطبيق الميجريشنز (أمر المالك الحرفي) — الدليل الوحيد: بوابة الحالة خضراء.
- كل ميجريشن جديد من 0102 فصاعدًا: فحصه في `scripts/db/migration_probes.py` بنفس الكوميت (قانون الفحوص) — والصفوف التقاعدية المشروعة تُزال بتوثيق (نمط 0083).
