## 1. ما وُجد بالفحص (قبل أي تعديل — قراءة الكود كما حلّلته 515 بكوميت `68652934`)

### 1.1 تعداد Auth Users عبر Admin API (`probe_session.auth_users_all`)
- كان يتبع `next_page` ويحترم سقفًا (100 صفحة × 200 مستخدم) — **لكن عند بلوغ السقف مع بقاء `next_page` يشير للأمام كان يكسر الحلقة ويعيد ما جمعه بصمت**: تعداد مقتطع يتدفق إلى `analyze()` كأنه كامل.
- `body.get("users") or []` كانت تُحوّل حمولة غير صالحة (users ليس قائمة) إلى قائمة فارغة بصمت — صفحة «فارغة» كاذبة مع `next_page` حي.
- `page = int(nxt)` بلا حراسة: `next_page` غير الرقمية تُفجّر `ValueError` غير موقّعة (رسالة بلا سياق القانون).
- لا فحص أن `next_page` **يتقدم** فعليًا (لو أعادت الـAPI رقم الصفحة نفسه تدور الحلقة حتى السقف ثم تُرجع جزئيًا).
- مدخل بلا `id` كان يختفي بصمت من المقارنة (`u.get("id")` = None) — والمقارنة كلها مفتاحها الـid.

### 1.2 تعداد profiles وsubscriptions عبر PostgREST (`accounts_orphan_audit.fetch_profiles` / `fetch_subscription_client_ids`)
- الصفحة القصيرة كانت (وما زالت) إشارة الانتهاء الصحيحة — **لكن عند بلوغ `MAX_PAGES` بكل الصفحات ممتلئة كانت الدالة تُرجع الجزء المجموع بصمت** (`return out` بعد الحلقة) بدل الرفض.

### 1.3 سير العمل (migration-state-audit.yml)
- الخطوة النهائية كانت تعرف `ORPHAN_RC` بقيمتين معنويتين فقط: 0 (CLEAN) وغيرها (ORPHANS) — **لا وجود لقيمة «التعداد غير المكتمل»**: تعداد مقتطع كان سيُعلن CLEAN طالما الدلاء صفرية على البيانات الناقصة.

### 1.4 لماذا هذا خطر حقيقي على الحكم (وتأطير الأمانة)
- قائمة auth مقتطعة قد **تخفي يتيمةً وراء السقف** (CLEAN كاذب) أو **تخترع يتيمة** (profile موجودة بلا auth ظاهريًا — RED كاذب). كلاهما حكم على بيانات جزئية، وكلاهما مرفوض.
- **الإنتاج اليوم بعيد عن كل السقوف** (31 auth مستخدمًا = صفحة واحدة من 200 · 31 profiles = صفحة قصيرة واحدة من 500 · 13 اشتراكًا = صفحة قصيرة واحدة من 1000) — هذه التقوية **قانون وقائي** ضد النمو المستقبلي وأي انجراف بعقد التقسيم من مزود الـAPI، وليست إصلاح عطل مُلاحظ حيًا؛ وحكم 515 الحي (CLEAN) **يبقى بنتيجته الأصلية دون أي تعديل** — وسيُثبت القانون الجديد اكتماله من جديد بتشغيلة البوابة على دفعة هذا الكوميت نفسها (الصفحة الوحيدة قصيرة/`next_page=null` تصلح إثبات اكتمال تحت القانونين القديم والجديد معًا).

## 3. القانون الجديد بالضبط (كما هو بالكود)
1. **Admin API (Auth Users):** الإثبات الوحيد للاكتمال = استجابة `next_page` فيها `null`/غائب. السقف (100 صفحة × 200) **شبكة أمان لا إشارة انتهاء** — بلوغه مع `next_page` حي = `EnumerationIncomplete`.
2. **PostgREST (profiles/subscriptions):** الإثبات الوحيد = **صفحة قصيرة** (< `PAGE` للـprofiles · < `SUBS_PAGE` للاsubscriptions). بلوغ السقف (50 صفحة) بلا صفحة قصيرة = `RuntimeError`.
3. **مسار الحكم:** أي `RuntimeError` من التعداد → `::error::` + **exit 3 (INCOMPLETE)** — الحكم محجوب، لا يُقرأ CLEAN ولا ORPHANS.
4. **البوابة:** `ORPHAN_RC=3` تُفشل التشغيلة برسالة صريحة (كما تفعل مع ORPHANS تمامًا).
5. **الحدود الهندسية مثبتة باختبار:** `test_pagination_geometry_and_exit_codes_pinned` يثبت 200×100 للـauth و500×50 و1000×50 — لا تتغير بهذا الإطار (رفعها قرار مستقل بمعرفة النمو الفعلي).
