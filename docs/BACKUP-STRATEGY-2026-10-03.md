## 2. نتائج التدقيق — ما الموجود، وما المشكلة

### 2.1 جواب مباشر: هل النسخ اليومي ضروري؟ — **نعم، إلزامي**

الدليل المقيس: Supabase Free لا يوفر **أي** نسخة احتياطية (`backups: []`, `pitr_enabled: false`). لو حُذف `db-backup.yml` اليوم لأصبحت قاعدة البيانات وصور المستخدمين **بلا أي نسخة على الإطلاق** — أول bad migration أو حذف جدول خطأ = فقدان نهائي. النظام اليومي ليس رفاهية ولا تكرارًا؛ هو خط الدفاع الوحيد القائم.

### 2.2 هل توجد نسخة احتياطية مكررة بلا فائدة؟

لا يوجد تكرار حرفي (لا artifacts، لا مستودع نسخ ثانٍ، لا snapshot مزدوج). الموجود أدق من وصف «التكرار»: **تراكم بلا قاعدة** — 29 لقطة DB كاملة + 14 نسخة ملفات كاملة في working tree مع أن قيمة الاستعادة اليومية تتركز في آخر أيام قليلة، والباقي «تاريخ» كان يمكن اختزاله بأسبوعي/شهري. تداخل وظيفي وحيد: `storage-inventory` (جرد) مقابل `storage-backup` (ملفات فعلية) — الجرد ~1 KB يوميًا وقيمته رصد النمو، يُبقى عليه (رخص ولا يستحق تعطيل آلية عاملة).

| # | العائق | الدليل المقيس | الأثر |
|---|---|---|---|

### 2.4 تقييم المُستهلك اليوم

التكلفة النقدية اليوم = **$0 فعلًا** (ريبو عام → دقائق مجانية؛ صفر artifacts؛ git غير مفوتر). مشكلة النظام الحالي **ليست الفاتورة** بل: غياب سقف النمو (BS-2/BS-3) + التمركز (BS-1/BS-4). أي خطة «تحسين» تعطّل النسخ اليومي تحمي الفاتورة وتُعرّض البيانات — الأولوية معكوسة تمامًا.

## 3. التصميم المقترح — الآلية الموحدة (Free/Hobby أولًا)

### 3.1 المبادئ الحاكمة

1. **فصل الطبقات:** GitHub الخاص = طبقة تشغيلية قصيرة المدى (استعادة سريعة لبضعة أيام) · Off-site (Google Drive) = طبقة نجاة طويلة المدى (تُنجو من فقدان GitHub نفسه).
2. **لا إعادة بناء لما يعمل:** النسخ اليومية الثلاث تبقى كما هي بلا تعديل — تُضاف طبقتان فوقها (Retention + Off-site)، لا تُستبدل.
3. **Free/Hobby صارمة:** GitHub $0 (ريبو عام) · Supabase Free بلا لمس · Vercel Hobby بلا لمس · **Google Drive ضمن فئته المجانية 15 GB بلا وسيلة دفع** — مع ميزانية داخلية ≤ 12 GB (تحفظ الحصة المشتركة §1.5 — قرار المالك 2026-10-04، كانت 8GB).
4. **طبقة رفع محايدة للمزود (rclone):** الأرشفة والتشفير وGFS مستقلة عن الوجهة — التبديل مستقبلًا بين Drive وR2 (أو أي S3-compatible) = تغيير secret/variable واحد بلا إعادة كتابة.
5. **قانون PII:** كل ما يغادر GitHub يُشفَّر جانب العميل إلزاميًا (المستودع الخاص يحمل أشد أنواع PII — صور وإيصالات)، والوجهة مجلد خاص بتوكن ضيق النطاق.

                  │  ① أسبوعيًا: backup-retention (GFS prune داخل المستودع الخاص)

### 3.3 خيار التخزين الخارجي — المقارنة الثلاثية والقرار (التحديث 2026-10-04)

| المعيار | **Google Drive (المعتمد — الأساسي)** | Cloudflare R2 (ترقية مشروطة) | Git mirror خارجي (P0-1 المجهز) |
|---|---|---|---|
| تجهيز المالك | OAuth publish-to-production (أو Service Account) + rclone token — **بلا وسيلة دفع** | تفعيل R2 (**يتطلب وسيلة دفع**) + bucket + توكن Object-RW | حساب جديد على مزود git + مستودعان + توكن |
| السعة المجانية | **15 GB** (مشتركة مع Gmail/Photos → ميزانية ≤12GB) | 10 GB مستقلة | بلا حد عملي (git كامل) |
| البصمة | أرشيفات مشفرة انتقائية (أصغر بصمة) | مثل Drive | تاريخ git كامل دائمًا (الأضخم) |
| استقرار المصادقة | **المعتمد بقرار GD-0: Service Account** — مفتاح ثابت بلا شاشة موافقة ولا انتهاء 7 أيام (أثبت من OAuth الذي تحفظ §1.5-2 يمنعه) | مفاتيح S3 ثابتة (الأثبت) | توكن ثابت |
| Egress عند الاستعادة | مجاني (حساب شخصي، حدود API بعيدة المنال بأحجامنا) | مجاني دائمًا | مجاني |
| Retention | GFS آلي بالمفاتيح عبر rclone | مثل Drive | تاريخ git يتراكم كاملًا |
| متى يُفعَّل | **الآن (بقرار المالك — GD-0)** | فقط عند شرط §3.6 | خطة بديلة فورية إن رفض المالك Drive كليًا |

**القرار (تحديث 2026-10-04):** Google Drive هو **المسار الأساسي** — يغلق BS-1/BS-4 بلا بطاقة دفع وبسعة أكبر من الفئة المجانية لـ R2. **R2 لا يُلغى من الخطة** بل يُحوَّل إلى مسار ترقية مشروط (§3.6)؛ والـ git mirror الجاهز يبقى خطة بديلة فورية. لا يُشغَّل مساران معًا إلا بقرار مالك (ازدواجية غير ضرورية).

### 3.4 Retention المعتمد — GFS (Grandfather-Father-Son) بدل 30 نسخة كاملة متراكمة (بدون تغيير)

| الطبقة | القاعدة | DB snapshots | Storage backups | الجرد (census) |
|---|---|---|---|---|
| **Daily (ابن)** | آخر 7 أيام فقط | 7 | 7 | 7 |
| **Weekly (أب)** | نسخة كل أحد — آخر 5 أسابيع | 5 | 5 | 5 |
| **Monthly (جد)** | أول يوم بالشهر — آخر 6 أشهر | 6 | 6 | 6 |
| **الحصيلة القصوى في working tree** | | **18 نسخة** (بدل 29+ غير المنتهية) | 18 | 18 |

- **على Google Drive:** أرشيف أسبوعي احتفظ بآخر **8** · أرشيف شهري احتفظ بآخر **6** + **bundles شهرية: آخر 6** (كود المستودعين).
- **الحصيلة العملية:** من متوسط تراكم 30 نسخة/شهر متصاعد → سقف ثابت 18 نسخة (working tree)، وأسوأ حالة فقدان بيانات = يوم واحد (النسخ اليومية موجودة دائمًا).
- **أفق الاستعادة:** يومي = 7 أيام (داخل GitHub) · أسبوعي = ~شهرين (8 نسخ على Drive) · شهري = 6 أشهر — ويتمدد أبعد عبر تاريخ git داخل المستودع الخاص (حتى قرار BS-5).
- **قاعدة الحذف آمنة:** الحذف من working tree فقط عبر workflow مخصص؛ تاريخ git يبقى كما هو (BS-5 مؤجل بقرار منفصل إذا لزم).
- **صمّ القواعد كمتغيرات** (نسق `notifications-prune.yml` القائم): `BACKUP_RETENTION_DAILY=W` قابل للضبط من Settings بلا تعديل كود.

  monthly/ 2026-11.backups.bundle.age      (git bundle للمستودع الخاص)

**حساب السعة (أساس مقيس: لقطة DB 9.5 MB خامًا → ~2 MB مضغوطًا · ملفات 4.5 MB شبه غير قابلة للضغط · bundle الريبو العام ≈ 286 MB):**

| النوع | الحجم الواحد | العدد المحتفظ | الإجمالي |
|---|---|---|---|
| أرشيف بيانات أسبوعي (DB+ملفات+جرد) | ~6.5–7 MB | 8 | ~55 MB |
| أرشيف بيانات شهري | ~7 MB | 6 | ~42 MB |
| bundle شهري — alkemos | ~290 MB (يكبر مع الريبو) | 6 | ~1.74 GB |
| bundle شهري — musclehubeg-backups | ~10–30 MB | 6 | ~0.12 GB |
| **الإجمالي المستقر** | | | **~2.0 GB ≈ 13% من 15 GB** |

- **أسوأ سيناريو نمو** (تضاعف الريبو العام + ثلاثة أضعاف البيانات): ~3.7 GB (~25%) — لا يزال بعيدًا عن الميزانية.
- **حواجز منع الامتلاء (إلزامية):** (أ) سقف صاخب 12 GB — الـ workflow يقيس حجم المجلد قبل الرفع ويفشل بصوت عالٍ عند التجاوز بدل ملء الحصة · (ب) تقرير حجم شهري في سجل التشغيل · (ج) إن تجاوز bundle الكود ~400 MB لكل نسخة → تقليص الشهري إلى 3 bundles أو التحول لبundles تزايدية (قرار GD-5) · (د) حارس الحصة يُقاس على **حجم مجلد النسخ نفسه** لا على `rclone about` (قياس GD-1: عنصر about لحساب خدمة = أصفار بالتصميم — البايتات تُحسب على حساب مالك المجلد؛ الحارس مطبّق داخل `gdrive-smoke-test.yml`: `size --json` → فشل صاخب عند تجاوز 12 GB).
- **التشفير إلزامي قبل مغادرة GitHub** (age أو openssl AES-256) — مفتاح مستقل `BACKUP_ENCRYPTION_KEY` في Secrets، **مع قرار حفظ خارجي للمفتاح** (مدير كلمات مرور لدى المالك): المفتاح داخل GitHub وحده يعني فقدانه مع فقدان الحساب — نفس العطل الذي نعالجه.
- **الرفع عبر rclone** (نفس الأداة تخدم R2 مستقبلًا — مبدأ §3.1-4) — **مثبتة داخل الـ workflow بإصدار مقيد وبوابة SHA256** (v1.75.1 + البصمة مثبتتان في `gdrive-smoke-test.yml`) لأنها غير مسبقة التثبيت على عدّاءات GitHub (قياس 2026-10-04) · تحذير تسمية موثق: متغيرات البيئة للتنقيط تستخدم بادئة `PINNED_RCLONE_*` وليس `RCLONE_*` — rclone يفسر `RCLONE_<NAME>` كأنه علم `--<name>` (قياس: `RCLONE_VERSION` اصطدم مع `--version`). آلية المصادقة — **قرار GD-0 (2026-10-04): الخيار (ب) Service Account** عبر السر `GOOGLE_DRIVE_SERVICE_ACCOUNT_JSON` — توكن ثابت بلا شاشة موافقة ولا انتهاء 7 أيام، وصلاحيته محصورة بمشاركات المجلدات لـ SA (أقل صلاحية فعليًا) · متطلب تفعيل: Drive API **مفعّلة** (فعّلها المالك — قياس تشغيل 37168415521) · **قانون نهائي مقيس بعدها: الـ SA لا يملك حصة تخزين أصلًا ولا يستطيع إنشاء ملفات على حساب Drive استهلاكي حتى داخل مجلد مشترك بدور Editor (403 storageQuotaExceeded — البايت يُحسب على مالك الملف وهو الـ SA بلا حصة؛ تشغيلات 37168415521 لمساحة الـ SA نفسها + 37168880937/37169086366 للمجلد المشترك)** → كتابة SA ممكنة فقط عبر Workspace shared drive (مدفوع) — قرار مسار الرفع (OAuth / Workspace / R2) معلق على المالك (§5 + GD-1-ALT).
- **الأسرار الجديدة المطلوبة (2 فقط):** `GDRIVE_RCLONE_CONFIG` (إعداد remote كاملًا كـ JSON — أو `GDRIVE_SA_JSON` لمسار SA) · `BACKUP_ENCRYPTION_KEY` — تُوثق مصادرها في `docs/RECOVERY-SECRETS-SOURCES.md` عند التنفيذ. الأسرار القائمة (`BACKUP_REPO_TOKEN`, `SUPABASE_SERVICE_ROLE_KEY`, `NEXT_PUBLIC_SUPABASE_URL`) تُعاد استخدامها كما هي — لا تدوير ولا لمس.

### 3.6 مسار الترقية المشروط إلى R2 (متى يُعاد التفعيل)

R2 يبقى في الخطة كوجهة ترقية جاهزة التصميم (طبقة rclone محايدة) ويُفعَّل فقط عند تحقق أي شرط: (أ) اقتراب الاستخدام من ميزانية 12 GB مع تعذر التقليص · (ب) هشاشة تشغيلية مثبتة في مصادقة Drive (انتهاء refresh tokens رغم نشر شاشة الموافقة) · (ج) حاجة مستقبلية إلى SLA/مفاتيح ثابتة مع توفر وسيلة دفع. عند التفعيل: bucket خاص + توكن Object-RW ضيق + `R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY` — ثم تبديل الـ remote وحده بلا أي تغيير في الأرشفة/التشفير/GFS.

## 6. ما التُزم به في إطار 2026-10-04 (تنفيذ GD-0 + GD-1)

نُفّذ: قرارات GD-0 كما وثّقت أعلاه · تحديث هذه الخطة (حارس الحصة 12 GB + توثيق آلية SA والقياسات الحية) · workflow الاختبار الدخاني `gdrive-smoke-test.yml` (dispatch-only) + صفّه في `docs/CI_GATES.md` · توثيق مصدر السر الجديد في `docs/RECOVERY-SECRETS-SOURCES.md` · سجل `worklog.md` + صف السجل في `docs/README.md` (قانون born-archived) · فحوص العملية على فرع مؤقت `gd1-smoke-test` قبل أي دفعة إلى main — لا شيء يهبط على main قبل جولة اختبار خضراء. **بعد أن فعّل المالك الـ Drive API وشارك مجلد «Alkemos Backups» (Editor)، قاس الاختبار الدخاني القانون النهائي: الـ SA لا يستطيع إنشاء ملفات على حساب استهلاكي (403 storageQuotaExceeded)** → جولة خضراء مستحيلة التحقيق تحت قيد SA على Drive استهلاكي. **ثم توجيه المالك بالمعرف (نفس اليوم — سر `GDRIVE_FOLDER_ID` + إعادة تسمية الفولدر «AlkemosBackups»): قياس التشغيلين 37170955147/37171157963 حسم النظرية — الاستهداف بالمعرف لا يغيّر مالك الملف المُنشأ (الـ SA) وهو طرف الحصة الصفرية، فالمشاركة المثالية (canAddChildren=True) والمعرف المُثبَّت لا يرفعان حاجز الـ 403 أبدًا** → كل عمل الفرع (الـ workflow بتوجيه المعرف + التوثيق + تحديث هذه الخطة) **يبقى خارج main بانتظار قرار المالك في آلية الرفع** (§5: OAuth / Workspace shared drive / R2 — والـ workflow الآن يدعم مسار Workspace shared drive تلقائيًا لو اختُبر).

لم يُنفّذ ولن يُنفّذ قبل أمر مالك: أي رفع فعلي للنسخ أو Retention أو حذف أي نسخة قائمة (GD-2+) · إنشاء/تعديل أي bucket · أي مساس بـ Production أو DNS أو Vercel أو Supabase أو Cloudflare · أي كشف لقيمة السر في أي مخرج أو مستودع — القيمة تُقرأ فقط داخل عدّاء GitHub Actions المؤقت (ملف 0600 يُحذف بنهاية التشغيل، وكل مخرجات السجل معقّمة من حقول الـ SA). علامة `[vercel skip]` على كل دفعة توثيقية (نمط التوثيق القائم — آخر docs-commit أنتج نشرًا CANCELED بلا خدمة، مؤكد في `docs/VERCEL-BACKUP-MIGRATION-PLAN-2026-10-03.md` §1).
